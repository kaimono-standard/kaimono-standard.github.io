# 新旧比較記事の編集ルール

`facts.json` の `article_type` が `"version"` のときに使う。Codex の下書きプロンプトには、このファイルの全文と、`editorial-rules.md` の「## 文体」以降（文体・書いてよいこと・プレースホルダ・セルフチェック）を続けて渡す。5機種比較の「構成」はこの型では使わない。

## 記事の役割

読者は「新しいモデルが出たけれど、安くなったひとつ前のモデルで足りるのでは」と迷っている人。検索では「A B 違い」「A 型落ち」と打つ。記事の仕事は、公式仕様を1項目ずつ並べて**何が変わって、何が変わっていないか**をはっきりさせ、価格差に見合うかを読者が判断できるようにすること。新型を勧める記事ではない。違いが小さければ「旧型で足りる人が多い」と書いてよい。

## 対象にしてよい組み合わせ（企画の段階で確認する）

- 同じメーカーの同じシリーズで、**メーカーが公式に後継・新モデルと示している**こと。根拠のページ（ニュースリリース、製品ページの「従来機種」表記、比較表など）を `successor_evidence` に入れる。根拠がなければ「後継」とは書かず、この型の記事にもしない
- 旧型が楽天市場で**新品として複数の店舗で**扱われていること。旧型がもう買えないなら比べる意味がない
- 型番の末尾違いだけの販路別モデル（量販店モデル・ネット限定モデル）は新旧ではない。この型では扱わない

## 構成（exemplar-version.tpl.html と同一にする）

1. `review-header`：カテゴリ、h1、リード文、署名、広告表記
2. `review-hero-image version-hero`：新型・旧型の画像2枚と `version-tag`
3. `review-summary`：見出しは「新型と旧型、どちらを選ぶか」。2行（`#new` と `#old`）と、価格差の一文（`{{PRICEDIFF:新型key:旧型key}}`）
4. `#diff` 仕様の違いの表：列は「項目 | 新型 | 旧型」。先頭行は発売時期。`table_columns` の順に全項目を並べ、**値が違う行だけ** `class="is-diff"` と `<span class="diff-mark">違い</span>` を付ける。最後の行は楽天市場の掲載時価格
5. `#changes` 変わったところ：`changes` の項目ごとに `plain-guide` の article。新旧の値を台帳のまま書き、どんな使い方の人に関係するかを添える
6. `#unchanged` 変わらないところ：同じ値の項目を短くまとめる
7. `#products` 2機種の詳細：`id="new"` と `id="old"` の `review-product`。構造は5機種比較の製品ブロックと同じ
8. `#sources` 出典：新型・旧型の `official_url` と、`successor_evidence.url`
9. サイドバー：目次、比較の前提、関連する比較

h1 は「［ブランド］［新型の型番］と［旧型の型番］の違い。［軸A］・［軸B］で選ぶ」。軸は `changes` のうち読者への影響が大きいものから2つ。`<title>` は h1 の「。」を「｜」にし末尾に「｜買いもの標準」。

完成例の `modelNew` `modelOld` は仮のキー。**必ず台帳の products の key に置き換える**（`products` の1つ目が新型、2つ目が旧型）。

## この型で特に守ること

- 「違い」の印は、台帳の `specs` で新旧の値が**文字列として違う**行だけに付ける。表記ゆれ（「約1.0kg」と「約1kg」）は台帳側で揃えてから書く
- 新旧の差を計算して書くのは、両方の値が台帳にあり単位が同じときだけ（「約100g軽くなった」）。片方しかない項目は「旧型は公式仕様に記載がありません」と書く
- 「進化」「大幅に向上」「劇的に」などの評価語は使わない。何がどう変わったかだけを書く
- 旧型について「お買い得」「今が買い時」と書かない。価格は変動するので、価格差の事実だけを示す
- 旧型の製品ブロックの `caution-note` には、在庫がなくなり次第販売が終わること、保証や修理の扱いは販売店とメーカーの表示を確認すること、のどちらかを必ず入れる
- 共通のセルフチェックにある「すべて5つ」は、この型では「製品ブロック2つ・結論2行・出典3行（新型・旧型・後継の根拠）」と読み替える。比較表の行数は `table_columns` の数＋発売＋価格
