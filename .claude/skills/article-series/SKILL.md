# 記事案を順番に記事にする

`article-ideas` が出した記事案を、1本ずつ最後まで仕上げて承認キューに出し、次の案に進む。**本数より品質を優先する**。前提が崩れた案は無理に書かず、理由を残して止め、次の案に進む。

1本の作り方そのものは `rakuten-comparison-article` の手順（企画 → 公式仕様 → 楽天・Amazon リンク → Codex 下書き → プレビュー → 事実照合 → 機械検証 → 提出）に従う。このスキルが足すのは、次の3つ。

1. **順番と進み具合の管理**：`_ideas/<日付>/queue.json`。途中で会話が要約されても、キューを読めば続きから再開できる
2. **記事案の引き継ぎ**：記事案の切り口・狙う検索語・注意・反対意見への答えを、台帳の `brief`（企画メモ）として Codex に渡す。brief は書き方の方針で、事実の根拠にはならない（照合には渡さない）
3. **品質の関所**：`references/quality-gates.md` の G0〜G5。どれか1つでも通らなければ提出しない

公開はユーザーが承認画面で承認したときだけ。このスキルは提出（承認待ち）までで止まり、承認を待たずに次の案に進む。

## 始め方

```bash
# キューを作る（初回だけ）。順番は締め切りが近い順（在庫が消えそうな新旧比較、季節の山が早いもの）
node .claude/skills/article-series/scripts/queue.mjs init _ideas/<日付> --order 6,1,7,5,2,3,4,8
# 進み具合
node .claude/skills/article-series/scripts/queue.mjs status
```

順番は、(1) 旧型の在庫が消えそうな新旧比較、(2) 需要の山が早い季節もの、(3) 残り、の順で決める。同じ担当の記事が続かないように並べる。

## 1本ごとの流れ

各記事の前に必ず次の2つを実行する（差し戻しがあれば、それを先に直す）。

```bash
node .claude/skills/article-series/scripts/queue.mjs sync   # 承認画面の結果（公開・差し戻し）を反映
node .claude/skills/article-series/scripts/queue.mjs next   # 作業中の案か、次の案を表示
```

| # | 工程 | 中身 | 通らなかったら |
|---|---|---|---|
| G0 | 着手前の前提確認 | 記事案の前提（公式仕様が文字で取れる／楽天で公式店か大手が新品を通常価格で扱う／新旧比較なら後継として見られている根拠と旧型の在庫）を、**今日の時点で**確かめ直す | 製品の差し替えで救えるなら差し替える。救えなければ `set <n> blocked --note "理由"` にして次へ |
| — | 開始 | `queue.mjs start <n> --slug <slug>` で `_drafts/<slug>/facts.json` に brief・型・担当が入る | |
| — | 台帳づくり | `rakuten-comparison-article` の手順1〜3b（製品選定・公式仕様・楽天リンク・Amazon） | |
| G1 | 台帳の独立監査 | 台帳を作っていないサブエージェントが、公式ページと楽天の商品ページを開き直して、台帳の値を1つずつ照らす | 台帳を直して G1 をやり直す |
| — | 下書き・プレビュー | `codex-draft.mjs` → `wire.mjs --preview` | |
| G2 | 事実照合 | `codex-factcheck.mjs --preview` で **high も medium もゼロ**になるまで直す（提出の条件は high ゼロだが、このスキルは medium も残さない） | 表現を弱めるか削る。台帳で裏付けられるなら台帳を直す |
| G3 | 読者目線の独立レビュー | 下書きを書いていないサブエージェントが、検索意図・結論と表の一致・執筆者の声・AI感・brief の注意の反映を採点する。再レビューは同じレビュアーに続けて頼み、前回の指摘が直ったかと新しい重大な問題だけを見てもらう | 指摘を直して G2 からやり直す |
| G4 | 機械検証 | `verify.mjs <slug> --preview` | 直してやり直す |
| G5 | 提出前の最終確認 | 在庫と価格の再確認（新旧比較は特に）、タイトル・説明文・リードを読み直す | 直す |
| — | 提出 | `node admin/submit.mjs _drafts/<slug>` → `queue.mjs set <n> submitted` | |

各関所の中身・サブエージェントに渡す指示・合格の基準は `references/quality-gates.md` にある。G1 と G3 のレビュアーには、他の関所の結果を見せない（同じ見落としを重ねないため）。

G2 と G3 を3周回しても収まらないときは、無理に提出しない。`set <n> blocked --note "何が残ったか"` にしてユーザーに報告し、次の案に進む。

## 連続で回す

ユーザーが「全部」「連続で」「自動で」と頼んだら、キューが空になるまで**止まらずに**次の案へ進む。1本提出するたびにユーザーの返事を待たない（報告は短く出して、そのまま次の案の `sync` → `next` に進む）。

止まってユーザーに聞くのは、次のときだけ：
- 楽天アフィリエイト管理画面や Amazon のログインが切れている（パスワードは入力しない。ユーザーにログインを頼む）
- 同じ種類の失敗が続き、関所の基準を下げないと進めない状態が2本以上続いた
- 承認画面の差し戻しで、方針の判断が要る理由が書かれている

止めた案（blocked）は、止めた理由を残して次の案に進むだけでよい。聞く必要はない。

## 進め方の決まり

- **1本ずつ最後まで**。2本を同時に作りかけにしない（`start` は作業中の案があると止まる）。ただし Codex の下書きや事実照合を待つ間に、次の案の G0 をサブエージェントに調べさせるのはよい
- **記事案は鵜呑みにしない**。ideas.md の価格・在庫・日付は記事案を作った日のもの。G0 で必ず取り直す。候補製品の例は仮で、選び直してよい。記事案と違う判断をしたら、`queue.mjs set` の `--note` か台帳の `pick_reason` に理由を残す
- **brief の数値を記事に書かない**。記事に書く事実は、台帳に入れて G1 を通したものだけ
- **担当は記事案どおり**。ただし G0 で切り口が変わり、別の執筆者の視点のほうが読者に近くなったら変えてよい（`facts.editor` を直し、理由をメモする）
- **関連記事**：`facts.related` には、同じ読者が次に読む既存記事を2本選ぶ。キューの中で先に提出した記事は、まだ公開されていないのでリンクしない
- 共有ファイル（config.js・記事一覧など）に触らない。配線は承認時に publisher が行う

## 報告

1本提出するごとに、ユーザーへ2〜3行で伝える：タイトル・担当・製品（新旧比較なら2機種）・公式で確かめられず記事に書かなかった項目・承認画面で見てほしい点。止めた案は理由を1行で伝える。

キューを最後まで回したら、`queue.mjs status` の結果を元に、提出・止めた・差し戻しの一覧を日本語でまとめる。

## やってはいけないこと

- 関所を飛ばす、合格の基準を下げる（「medium なら残してもいい」「G3 は省略」など）
- 前提が崩れた案を、根拠の弱い製品や表現で埋めて提出する。止めて次に進むほうがよい
- 新旧比較で、後継の根拠（`successor_evidence`：メーカーの表示か、独立した情報源2件以上）が取れないのに新旧比較の型で書く。取れなければ、型を変えて成り立つかを考え、成り立たなければ止める
- メーカーが後継と明記していないのに、「メーカーが後継と発表」と読める書き方をする
- 承認を待たずに公開する、自分でコミット・push する
- キュー（queue.json）を手で書き換える。状態の変更は必ず `queue.mjs` で行う
