# 品質の関所（G0〜G5）

1本ごとに、上から順にすべて通す。どれか1つでも基準に届かなければ提出しない。G1 と G3 は**その工程を担当していないサブエージェント**（general-purpose）に任せ、他の関所の結果や Claude の見立ては渡さない。渡すのはファイルのパスと、下の指示文だけ。

---

## G0 着手前の前提確認（記事案が今日も成り立つか）

記事案の「なぜ今」「実現性」は記事案を作った日の情報。書き始める前に、今日の時点で次を確かめる。Claude が自分で調べても、サブエージェントに調べさせてもよい（前の記事の Codex 待ちの間に回すと速い）。

| 確かめること | 基準 |
|---|---|
| 公式仕様 | 候補製品それぞれに、比べる項目の数値が**文字で**載ったメーカー公式ページがある（画像だけは不可。取説PDFの仕様ページは可） |
| 楽天の取り扱い | 各製品を、メーカー公式楽天市場店か大手（量販店など）が**新品・通常価格**で扱っている。クーポン前提の価格、中古・アウトレット・並行輸入だけの製品は外す |
| 新旧比較 | 新型が旧型の後継として見られている根拠（`successor_evidence`）がある：メーカーの公式表示（1件で可、最優先）か、互いに独立した専門メディア・大手量販店・価格.com の後継表示が2件以上。旧型の新品が楽天の大手2店以上に残っている |
| 規制 | 記事の中心が効能・効果にならない。電気製品は、国内メーカー（国内の販売元）の製品を公式店・大手が新品で売っているものなら可。聞き慣れない輸入ブランドは、商品ページか取扱説明書で PSE 表示を確かめ、確かめられなければ外す |
| 既存記事との重複 | `search-index.js` の既存記事、キューで先に提出した記事と、読者も製品もかぶらない |

- 5製品比較で候補が外れたら、記事案の切り口（brief の title_draft・cautions）を守ったまま別の製品に差し替える。5製品が揃わなければ止める
- 新旧比較の後継の根拠は、まずメーカー（製品ページ・ニュースリリース・比較表・サポートページ）で探す。無ければ、世間が後継として見ているかを確かめる：専門メディアの記事、大手量販店の商品ページの「後継機種」表示、価格.com の後継・前モデル表示から、互いに独立した2件以上（`kind: "media"`）。個人ブログ・SNS・口コミは数えない。メーカーが新旧を別の位置づけで並べて売っているなら、世間の見方より公式を優先して止める
- どちらも取れなければ止める（`set <n> blocked --note "後継の根拠が1件のみ"` など）。5製品比較の中の1節にするなど、別の記事案として成り立つならユーザーに提案する
- 止めた理由は具体的に残す（「旧型の新品が楽天ビック1店のみ」など）。次回の記事案の材料になる

## G1 台帳の独立監査

台帳（`facts.json`）の値が公式ページと楽天の商品ページに本当に書いてあるかを、台帳を作っていない目で照らす。記事の数値はすべて台帳から来るので、ここが一番効く。

サブエージェントへの指示文（`<slug>` を置き換える）：

> あなたは比較記事の台帳を監査する担当です。`D:\ラクヨコ\_drafts\<slug>\facts.json` を読み、products のそれぞれについて、`official_url` のページを自分で開き直して（`node .claude/skills/rakuten-comparison-article/scripts/fetch-page.mjs <URL>` か WebFetch。取れなければ Chrome）、`specs` `features` `release` `caution_hint` `variant_note` の値が、公式ページの記載と一致するか1つずつ確かめてください。`successor_evidence` があれば、その `url` と `supporting` の各 URL に quote の文が本当にあるか、`kind` が media なら情報源どうしが独立しているか（同じ記事の転載でないか）も確かめてください。
> 次に `rakuten.item` の楽天の商品ページを開き、商品名に台帳の型番（`model`）が含まれるか、新品か、選択式なら台帳の製品が選べるか、中古・アウトレット・訳あり・セット品でないかを確かめてください。
> 判定：一致（表記ゆれは可）／不一致（公式の記載を引用）／公式に記載なし／ページが開けない。推測で「たぶん合っている」としないこと。
> 返すもの（JSON）：`{"checked": 件数, "issues": [{"product": key, "field": "specs.質量", "ledger": "約2.1kg", "official": "約2.2kg", "source": URL, "verdict": "mismatch|not_found|unreachable|rakuten_mismatch"}]}`

合格の基準：`issues` がゼロ。`unreachable` は Claude が Chrome で開いて確かめ、確かめられなければその値を `unverified` に移す。値を直したら、直した製品だけもう一度監査させる。

## G2 事実照合（Codex）

```bash
node .claude/skills/rakuten-comparison-article/scripts/wire.mjs _drafts/<slug> --preview
node .claude/skills/rakuten-comparison-article/scripts/codex-factcheck.mjs _drafts/<slug> --preview
```

合格の基準：`factcheck.json` の issues が **high・medium ともにゼロ**。low は1件ずつ読み、直すか、直さない理由を言えるものだけ残す。

直し方の順番：台帳で裏付けられる → 台帳に根拠を足して G1（その項目だけ）を通す。裏付けられない → 記事の表現を弱めるか削る。「公式仕様に記載はありません」への言い換えが定石。

## G3 読者目線の独立レビュー

下書きを書いていない目で、読者にとって良い記事かを見る。事実性は G1・G2 で見たので、ここでは見ない。

サブエージェントへの指示文：

> あなたは比較メディア「買いもの標準」の編集デスクです。`D:\ラクヨコ\_drafts\<slug>\preview.html` を、この記事を検索で見つけた読者のつもりで読み、次の観点で 1〜5 点を付けてください。判断材料として、`_drafts\<slug>\facts.json` の `brief`（企画メモ：狙う検索語・注意・反対意見への答え）と `editor`、執筆者の人物像（`_editorial\editors.json` の該当 id の public と internal）、編集ルール（`.claude\skills\rakuten-comparison-article\references\editorial-rules.md`、新旧比較なら `editorial-rules-version.md` も）、同じ型の完成例（`assets\exemplar.tpl.html` か `assets\exemplar-version.tpl.html`）を読んでください。
>
> 1. 検索意図：brief の target_queries で来た人の疑問に、最初の画面（リードと結論ブロック）で答えているか
> 2. 結論の筋：結論ブロック・用途別の説明・比較表の数値が、互いに食い違っていないか。「向いている人」が製品ごとに重ならず、表の数値から納得できるか
> 3. 執筆者の声：人物像の視点（何を先に確認するか、どんな場面で使うか）が記事全体に出ているか。完成例の文体をなぞっているだけになっていないか。使った・試したという体験を書いていないか
> 4. AI感のなさ：下の「AI感の目安」に当たる書き方がないか。人の編集者が書いた記事として読めるか
> 5. 企画メモの反映：brief の cautions（避ける書き方・必ず書くこと）と objection_answer が守られているか
> 6. 読みやすさ：一文が長すぎないか、同じ言い回しの繰り返し、専門用語の説明不足、スマホで読んで段落が重すぎないか
> 7. 買う前の不安：読者が買う前に確かめるべきこと（サイズ・対応・選択式の注意・旧型の在庫など）が、該当する製品の注意書きにあるか
>
> 返すもの（JSON）：`{"scores": {"intent": n, "logic": n, "voice": n, "no_ai_feel": n, "brief": n, "readability": n, "buyer_risk": n}, "issues": [{"where": "該当箇所の引用（30字以内）", "problem": "何が問題か", "fix": "具体的な直し方（書き換え案があれば）"}]}`。
> 新しい数値や事実を書き足す直し方は提案しないこと（記事に書けるのは台帳にある事実だけ）。

合格の基準：7項目すべて **4点以上**、かつ issues のうち直すべきものを全部直した。直したら G2 からやり直す（直しで事実が変わっていないかを照合し直すため）。

**再レビューは同じレビュアーに頼む**（毎回別のレビュアーにすると、そのたびに新しい好みの指摘が出て収束しないため）。1回目のレビュアーに SendMessage で続けて、次を頼む：

> 前回の指摘を直して preview.html を更新しました。記事全体を読み直し、(1) 前回の各指摘が直ったか（直った／直っていない／直し方で別の問題が出た）、(2) 前回は見落としていた重大な問題（事実の食い違い・検索意図に答えていない・読者が誤解する書き方）があればそれだけ、を挙げ、7項目を採点し直してください。好みの言い回しの指摘は新たに足さないこと。返す形は前回と同じ JSON に、各前回指摘の結果 `"previous": [{"where": "...", "status": "fixed|not_fixed|new_problem"}]` を加えたもの。

レビュアーの会話が切れて続けられないときだけ、新しいレビュアーに、前回の指摘一覧と直した内容を渡して同じことを頼む。

### AI感の目安（G3 で使う）

1つでもあれば直す。

- 締めの定型：「いかがでしたか」「参考になれば幸いです」「ぜひチェックしてみてください」「自分に合った〇〇を見つけましょう」
- 推量で包む：「〜と言えるでしょう」「〜ではないでしょうか」「〜かもしれません」を続けて使う
- 中身のない強調：「重要です」「ポイントです」「欠かせません」「見逃せません」の連発、「さまざまな」「幅広い」「多彩な」で具体を避ける
- 型どおりの並び：どの製品の説明も同じ文の形（「〜が魅力。〜も搭載。〜な人におすすめ」）で始まる、3つずつの列挙が続く
- 読者への過剰な呼びかけ：「〜ですよね」「〜ありませんか？」を段落ごとに入れる。リードで1回までにする
- 見出しの要約ラベル＋全角コロン（「結論：」「まとめ：」）
- 運営側・書き手が機械であることを匂わせる書き方：「本記事では〜を整理しました」を何度も言う、「データに基づいて」「客観的に」を自分で言う
- 感嘆符、絵文字、「！」で終わる見出し

## G4 機械検証

```bash
node .claude/skills/rakuten-comparison-article/scripts/verify.mjs <slug> --preview
```

合格の基準：「✓ 機械検証 OK」。最上級表現の一覧は、表の数値と目で照らす（同値があるのに単独の最上級になっていないか）。

## G5 提出前の最終確認

- **在庫と価格**：台帳の楽天リンクの商品ページを開き直し、新品の在庫があり、価格が台帳（`rakuten.price`）と大きく違わないことを確かめる。変わっていれば台帳を直して G2 からやり直す。新旧比較は旧型の在庫を特に見る
- **タイトル・説明文・リード**：狙う検索語の主な語がタイトルに入っているか。説明文（meta description）が記事の中身と一致しているか。タイトルは記事案の title_draft をそのまま使わなくてよい（製品が変わったなら合わせる）
- **関連記事**：`facts.related` の2本が公開済みの記事で、この記事の読者が次に読むものになっているか
- **日付**：`facts.date` が提出日（今日）になっているか。作業が日をまたいだら、台帳の date と `article.tpl.html` の日付（署名・JSON-LD・確認日）を揃えて直し、G2 からやり直す

すべて済んだら提出する。

```bash
node admin/submit.mjs _drafts/<slug>
node .claude/skills/article-series/scripts/queue.mjs set <n> submitted --note "G0〜G5 通過"
```
